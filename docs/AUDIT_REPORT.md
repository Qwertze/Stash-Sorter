# Stash Sorter source audit and verification

**20 November 2026.** The delivered hardened fork is labeled **1.12.3**. Its production sources compiled against an AquariusProxy Java 1.21.4 fat JAR, and its packaged entry point registered the expected configuration, five modules and command with a recording host. Release approval still needs the Gradle/Jupiter build on JDK 25, a complete dependency scan, the real Stash Manager suite and live proxy/world verification.

## Baseline and scope

The input archive contained 75 production Java source files, one Java template and 54 Java test/fixture files, a versioned recipe resource, Gradle wrapper, GitHub workflow and existing operator documentation. Discovery covered all source trees, build inputs, tests, CI and the changelog. Every production source was compiled. Detailed manual inspection concentrated on persistence, manager transport and authorization, order planning, the plugin entry point and build boundaries. The 13,732-line game adapter received structural review and compilation. Its individual tick transitions have not all been independently audited.

The initial wrapper could not download Gradle 9.5.0. Direct Java compilation, including the actual host annotation processor, succeeded. A baseline offline run exercised 454 ordinary test methods. Four new regressions then failed on the original order/parser code. Two additional numeric settings tests failed before their correction. Other findings below are supported by source inspection, resource integration tests or official advisories, as indicated.

### Interpreting the local measurement

The offline harness compiled temporary copies of the test sources with JUnit imports redirected to a small local assertion and reflection adapter. It ran a fresh instance per method, relevant setup/teardown callbacks and temporary-directory injection. It excluded only the real-server class. That is direct execution of the method bodies with a different runner. It does not establish JUnit discovery, platform behavior or exact Jupiter assertion-overload parity. The repository itself retains JUnit tests. No substitute JUnit library is shipped.

Separate copies of all production class files were instrumented with JVM bytecode probes. Lines are unique source-file/line pairs. Branch outcomes are the two arms of a conditional jump or distinct switch destinations. Constructors, lambdas and compiler-generated branches within owned classes count. Only generated BuildConstants was excluded. Counters cover the whole source tree, including unloaded classes. The original and final snapshots used the same measurement method. JaCoCo filters and line attribution can differ. The distributed JAR is uninstrumented.

## Unresolved risks and verification order

1. **Before deployment**, run `./gradlew clean build` and the dependency scan using a provenance-verified host JAR on JDK 25. Verify a compatible proxy with the Logback fix. Check the built artifact and compare its metadata and class ownership. Merge/branch protection is controlled by the repository owner.
2. **Exercise recovery with the real manager and a disposable Minecraft 1.21.4 world.** Prioritize starting/stopping during an in-flight job, reconnecting after a container click, changing dimension and cancelling a partially delivered order. Simulators do not model every server acknowledgement or cache timing.
3. **Close the coverage gaps.** The primary sorter reached 1.8% of lines in this run. Extract testable state transitions at the inventory and pathfinding boundaries as those behaviors change. Add coverage for dashboard apply conflicts, transport interruption, deny paths, index publication and genuine provider errors. The current region and whole-project targets remain unmet.
4. **Validate operational storage behavior.** Windows ACL inheritance and non-atomic filesystems were untested. Restrict access to old backups. Atomic replacement does not guarantee survival of sudden power loss. Concurrent mutation of nested stash objects and long-lived state across many stash names still need stress measurements.
5. **Review upstream changes.** Do not infer complete fat-JAR dependency coverage from a successful scan. The plugin supports one protocol line, while proxy implementation details and the separately deployed manager may change independently.
